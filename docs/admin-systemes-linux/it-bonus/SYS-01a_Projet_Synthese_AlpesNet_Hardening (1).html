🔒 Projet de synthèse — AlpesNet Hardening Suite

⏱️ Durée estimée : 6 à 10 heures selon l'ambition
📍 Mode : Autonome — fin de module SYS-01a
🎯 Public : Apprenants ayant terminé les kits 1 à 6 en avance
📦 Rendu : Dépôt Git ou archive ZIP dans Moodle

Contexte opérationnel
AlpesNet déploie régulièrement de nouveaux serveurs Linux pour ses équipes. Chaque déploiement manuel prend du temps, est source d'erreurs et produit des configurations légèrement différentes d'une machine à l'autre.

Tu es missionné pour concevoir une suite de scripts Bash qui automatise l'installation et la sécurisation complète d'un serveur Debian 12 fraîchement installé. Le résultat attendu : un administrateur peut cloner un dépôt, lancer un script principal, et obtenir en quelques minutes un serveur durci, configuré et audité — reproductible à l'identique.

🎯 Objectifs du projet

À l'issue de ce projet, tu seras capable de :

  • Concevoir une suite de scripts Bash modulaires, robustes et maintenables
  • Automatiser un processus de sécurisation complet et reproductible
  • Générer un rapport d'audit lisible par un humain et exploitable en production
  • Documenter un outil technique à un niveau professionnel
Ce projet n'est pas un kit guidé. Il n'y a pas de solution fournie, pas d'étapes numérotées à suivre. Tu fais des choix techniques, tu les justifies, tu les documentes. C'est exactement ce qu'on attend d'un administrateur d'infrastructures sécurisées.

🏗️ Architecture attendue

Le projet est organisé en modules indépendants orchestrés par un script principal.

#!/bin/bash
# hardening-suite/
#   main.sh                  ← point d'entrée unique
#   modules/
#     01-systeme.sh          ← mise à jour + outils de base
#     02-utilisateurs.sh     ← comptes, groupes, sudo
#     03-ssh.sh              ← durcissement SSH
#     04-firewall.sh         ← ufw + fail2ban
#     05-services.sh         ← désactivation services inutiles
#     06-logs.sh             ← rsyslog + logrotate
#     07-sauvegarde.sh       ← rsync + planification cron
#     08-audit.sh            ← génération du rapport final
#   config/
#     alpesnet.conf          ← variables de configuration
#   rapports/                ← rapports générés (gitignore)
#   README.md                ← documentation

Fonctionnement du script principal main.sh

main.sh doit :

  • Vérifier qu'il est exécuté en root (ou via sudo)
  • Lire la configuration depuis config/alpesnet.conf
  • Appeler chaque module dans l'ordre, en loggant le résultat de chaque étape
  • Accepter des arguments pour sélectionner les modules à exécuter : ./main.sh --modules 01,02,03 ou ./main.sh --all
  • Afficher un résumé en fin d'exécution : modules passés / échoués
  • Générer automatiquement le rapport d'audit en fin de run
# Exemple d'appel
sudo ./main.sh --all
sudo ./main.sh --modules 03,04,08
sudo ./main.sh --audit-only

📋 Cahier des charges — Modules obligatoires

Module 01 — Mise à jour système Obligatoire

  • apt update && apt upgrade -y avec gestion des erreurs
  • Installation des outils définis dans alpesnet.conf
  • Résultat loggé : nombre de paquets mis à jour, date, durée

Module 02 — Utilisateurs et groupes Obligatoire

  • Créer les comptes définis dans alpesnet.conf s'ils n'existent pas (idempotent)
  • Appliquer le principe du moindre privilège : sudo restreint, comptes service sans shell
  • Vérifier qu'aucun compte non défini n'a UID 0
  • Vérifier qu'aucun compte n'a NOPASSWD: ALL dans sudoers

Module 03 — Durcissement SSH Obligatoire

  • Appliquer les paramètres de durcissement depuis alpesnet.conf : PermitRootLogin, PasswordAuthentication, AllowUsers, MaxAuthTries
  • Vérifier la syntaxe avec sshd -t avant tout rechargement
  • Recharger SSH uniquement si la syntaxe est valide — ne jamais couper une session active sans vérification

Module 04 — Pare-feu et protection brute force Obligatoire

  • Configurer ufw : politique deny-incoming, règles depuis alpesnet.conf
  • Activer fail2ban avec la jail SSH, paramètres depuis alpesnet.conf
  • Vérifier l'état actif des deux services en fin de module

Module 05 — Services inutiles Obligatoire

  • Lister les services actifs, comparer à la liste autorisée dans alpesnet.conf
  • Désactiver tout service non listé (avec confirmation avant action si mode interactif)
  • Loguer les services désactivés et les ports fermés (avant/après)

Module 06 — Journalisation Obligatoire

  • Déployer une règle rsyslog dédiée aux événements SSH AlpesNet
  • Configurer logrotate avec la politique définie dans alpesnet.conf (rétention, compression)
  • Tester avec logger que la règle rsyslog est active

Module 07 — Sauvegarde Obligatoire

  • Configurer rsync pour sauvegarder /etc et les répertoires définis dans alpesnet.conf
  • Planifier la sauvegarde via cron avec redirection des logs
  • Générer un checksum sha256 et vérifier l'intégrité après chaque sauvegarde

Module 08 — Rapport d'audit Obligatoire

Le module 08 ne configure rien. Il vérifie et documente l'état du système après les autres modules. Il produit un fichier rapports/audit-[hostname]-[date].txt lisible par un humain et exploitable en production.

Le rapport doit couvrir :

⚙️ Fichier de configuration config/alpesnet.conf

Toutes les valeurs métier sont externalisées dans ce fichier. Les scripts ne contiennent aucune valeur en dur — ils lisent uniquement depuis alpesnet.conf.

# ============================================================
# alpesnet.conf — Configuration AlpesNet Hardening Suite
# ============================================================

# Identité du serveur
HOSTNAME="srv-alpesnet"
DOMAINE="alpesnet.local"

# Comptes à créer (format : login:groupe:shell:commentaire)
COMPTES=(
  "alice.martin:devops:/bin/bash:Alice Martin Lead DevOps"
  "www-nginx:www-nginx:/usr/sbin/nologin:Compte service Nginx"
  "backup-agent:backup-agent:/usr/sbin/nologin:Agent de sauvegarde"
)

# Groupes à créer
GROUPES=("devops" "readonly" "backup-agent" "www-nginx")

# Durcissement SSH
SSH_PERMIT_ROOT="no"
SSH_PASSWORD_AUTH="no"
SSH_ALLOW_USERS="adm-[prenom]"
SSH_MAX_AUTH_TRIES=3
SSH_LOGIN_GRACE_TIME=20

# Règles ufw (format : port/protocol:from)
UFW_RULES=(
  "22/tcp:192.168.56.0/24"
  "80/tcp:any"
)

# fail2ban
FAIL2BAN_BANTIME=3600
FAIL2BAN_FINDTIME=600
FAIL2BAN_MAXRETRY=3

# Services autorisés (tous les autres sont désactivés)
SERVICES_AUTORISES=("ssh" "rsyslog" "cron" "ufw" "fail2ban" "nginx")

# Journalisation
LOG_SSH_FILE="/var/log/alpesnet/ssh-auth.log"
LOGROTATE_RETENTION=14

# Sauvegarde
BACKUP_DIRS=("/etc" "/var/www")
BACKUP_DEST="/backup/alpesnet"
BACKUP_CRON="0 2 * * *"
BACKUP_RETENTION_DAYS=7

# Outils à installer
OUTILS_BASE=(
  "vim" "curl" "wget" "git" "tree" "htop" "lsof" "net-tools"
  "acl" "rsyslog" "logrotate" "ufw" "fail2ban"
  "nfs-kernel-server" "samba" "rsync" "nginx"
)

🔧 Exigences techniques — obligatoires

Robustesse

  • Chaque script commence par set -euo pipefail
  • Chaque module est idempotent : il peut être relancé plusieurs fois sans effet de bord (un compte déjà existant n'est pas recréé, une règle ufw déjà présente n'est pas dupliquée)
  • Chaque action risquée est précédée d'une sauvegarde automatique du fichier modifié (cp fichier fichier.bak.$(date +%Y%m%d%H%M%S))
  • Toute commande susceptible de couper l'accès SSH est testée avec sshd -t avant exécution

Logging

  • Chaque module produit des logs horodatés au format : [YYYY-MM-DD HH:MM:SS] [NOM_MODULE] [NIVEAU] message
  • Niveaux : INFO, OK, WARN, ERROR
  • Le log est écrit simultanément à l'écran et dans /var/log/alpesnet/hardening-[date].log

Documentation

  • Chaque script a son en-tête standard (Auteur, Date, Module, Objet, Usage, Dépendances)
  • Le README.md explique en moins d'une page : comment utiliser la suite, le format d'alpesnet.conf, la structure des rapports, et comment ajouter un nouveau module

Compatibilité

  • Cible : Debian 12 (Bookworm), installation minimale, VirtualBox
  • Aucune dépendance externe (Python, Ruby, etc.) — Bash pur + outils GNU standard
  • Le script principal détecte si la distribution est Debian et refuse de s'exécuter sur une autre

Traçabilité de l'exécution Obligatoire

Chaque exécution doit pouvoir être analysée a posteriori : quand un module a-t-il tourné, combien de temps a-t-il pris, est-il allé au bout.

  • Chronométrer chaque module individuellement (début, fin, durée) avec $(date +%s) ou $SECONDS
  • Logger la durée de chaque module dans le log principal au format : [NOM_MODULE] terminé en Xs (statut: OK/FAIL)
  • main.sh affiche un récapitulatif final avec la durée totale et la durée par module, trié du plus long au plus court
  • Le rapport d'audit (module 08) inclut un tableau des durées d'exécution de la dernière run
# Exemple de mesure dans un module
DEBUT=$(date +%s)
# ... actions du module ...
FIN=$(date +%s)
DUREE=$((FIN - DEBUT))
echo "[$(date '+%Y-%m-%d %H:%M:%S')] [03-ssh] [OK] terminé en ${DUREE}s" | tee -a "$LOGFILE"

Verrouillage et exécutions concurrentes Obligatoire

Deux lancements simultanés de main.sh (ou d'un module) sur le même serveur peuvent provoquer des corruptions de configuration. Le script doit l'empêcher.

  • main.sh crée un fichier verrou dans /var/lock/alpesnet-hardening.lock dès son démarrage
  • Le fichier verrou contient le PID du processus en cours (echo $$ > /var/lock/alpesnet-hardening.lock)
  • Si un verrou existe déjà au démarrage : vérifier que le PID contenu est toujours actif (kill -0 $PID)
    • PID actif → refuser de démarrer, afficher un message explicite et quitter (exit 1)
    • PID inactif (verrou orphelin d'un crash précédent) → avertir, supprimer le verrou obsolète et continuer
  • Le verrou est supprimé en fin d'exécution, y compris en cas d'erreur — utiliser un trap sur EXIT pour garantir le nettoyage
# Exemple de gestion du verrou
LOCKFILE="/var/lock/alpesnet-hardening.lock"

if [[ -f "$LOCKFILE" ]]; then
    OLD_PID=$(cat "$LOCKFILE")
    if kill -0 "$OLD_PID" 2>/dev/null; then
        echo "ERREUR : une exécution est déjà en cours (PID $OLD_PID)" >&2
        exit 1
    else
        echo "AVERTISSEMENT : verrou orphelin détecté (PID $OLD_PID inactif), nettoyage"
        rm -f "$LOCKFILE"
    fi
fi

echo $$ > "$LOCKFILE"
trap 'rm -f "$LOCKFILE"' EXIT

Séquencement et dépendances entre modules Obligatoire

Certains modules n'ont de sens que si un autre a déjà tourné avec succès. Le module 04 (pare-feu) ne doit pas s'exécuter si le module 03 (SSH) a échoué — sinon le risque est de fermer l'accès distant avant que SSH soit correctement durci et vérifié.

  • Définir une table de dépendances explicite, lisible en un coup d'œil (en haut de main.sh ou dans alpesnet.conf)
  • Avant de lancer un module, vérifier que tous ses prérequis ont le statut OK dans la run en cours
  • Si un prérequis est en échec ou n'a pas été exécuté : le module dépendant est sauté, pas exécuté en mode dégradé — logger clairement la raison du saut
  • --modules doit respecter cette table même si l'apprenant sélectionne manuellement un sous-ensemble de modules
# Exemple de table de dépendances (à placer en haut de main.sh)
# Format : [module]="dépendance1 dépendance2"
declare -A DEPENDANCES=(
    ["02-utilisateurs"]="01-systeme"
    ["03-ssh"]="01-systeme 02-utilisateurs"
    ["04-firewall"]="03-ssh"
    ["05-services"]="01-systeme"
    ["06-logs"]="01-systeme"
    ["07-sauvegarde"]="02-utilisateurs"
    ["08-audit"]=""   # aucune dépendance — peut toujours tourner
)

# Vérification avant exécution d'un module
verifier_dependances() {
    local module="$1"
    for dep in ${DEPENDANCES[$module]}; do
        if [[ "${STATUT[$dep]}" != "OK" ]]; then
            echo "[$module] SAUTÉ — dépendance '$dep' non satisfaite (statut: ${STATUT[$dep]:-non exécuté})"
            STATUT[$module]="SKIPPED"
            return 1
        fi
    done
    return 0
}

⭐ Extensions optionnelles — pour aller plus loin

Ces extensions sont bonus. Elles introduisent des concepts au-delà de SYS-01a. Elles ne sont pas évaluées sur les mêmes critères que les modules obligatoires — c'est l'exploration qui compte.

Option A — Module 09-auditd.sh : audit noyau Bonus

Installer et configurer auditd pour tracer les appels système critiques. → man auditd

  • Installer auditd et audispd-plugins
  • Ajouter des règles pour surveiller : modifications de /etc/passwd, /etc/sudoers, exécutions en root, connexions SSH
  • Intégrer la sortie ausearch dans le rapport d'audit module 08

Option B — Module 10-aide.sh : intégrité des fichiers Bonus

Installer AIDE (Advanced Intrusion Detection Environment) pour détecter toute modification non autorisée de fichiers système. → aide.github.io

  • Installer et configurer AIDE
  • Initialiser la base de référence (aide --init) après hardening
  • Planifier une vérification hebdomadaire via cron avec rapport par mail (ou dans le log)

Option C — Mode dry-run Bonus

Ajouter un mode ./main.sh --dry-run qui simule toutes les actions sans rien modifier, et produit un rapport de ce qui serait fait.

Option D — Gestion des erreurs avancée Bonus

Implémenter un mécanisme de rollback : si un module échoue, restaurer automatiquement les fichiers sauvegardés avant l'exécution du module.

Option E — Tests automatisés Bonus

Écrire un script tests/run_tests.sh qui vérifie chaque module de façon indépendante (peut s'appuyer sur bats-core).

🏁 Critères de validation — démonstration live

  • sudo ./main.sh --all tourne jusqu'au bout sans exit 1 non géré
  • Le rapport audit-[hostname]-[date].txt est produit et contient toutes les sections
  • sudo ./main.sh --all relancé une seconde fois sans modification → comportement identique (idempotence)
  • SSH est toujours accessible après exécution complète
  • sudo ufw status verbose montre les règles issues d'alpesnet.conf
  • Au moins un WARN ou FAIL est correctement détecté dans le rapport (ex : simuler un compte avec NOPASSWD avant le lancement)
  • Le récapitulatif final affiche la durée de chaque module et la durée totale
  • Lancer main.sh deux fois en parallèle dans deux terminaux → le second lancement est refusé avec un message explicite citant le PID en cours
  • Supprimer artificiellement le fichier verrou pendant une exécution puis relancer après un kill -9 du premier process → le verrou orphelin est détecté et nettoyé automatiquement
  • Forcer l'échec du module 03 (ex : renommer temporairement sshd) puis lancer --all → le module 04 est bien sauté avec un message explicite, pas exécuté en mode dégradé

💡 Conseils avant de commencer

Ne pas partir du résultat. Commence par écrire main.sh avec des appels vers des modules vides (echo "Module 01 - TODO"). Valide que la structure fonctionne, puis implémente module par module. Un projet bien architecturé avec deux modules complets vaut mieux qu'un monolithe de 400 lignes qui plante au milieu.
  • Commence par le module 08 (audit) — savoir ce que tu vas vérifier en aval guide ce que tu configures en amont
  • Teste chaque module isolément avant de l'intégrer à main.sh : sudo bash modules/03-ssh.sh
  • Utilise ShellCheck systématiquement — il capte 80% des erreurs Bash classiques avant exécution
  • Snapshot VirtualBox avant chaque test de module risqué (SSH, ufw)
  • L'idempotence est le vrai défi — tester toujours le second run : le script ne doit pas créer un compte qui existe déjà, ni ajouter une règle ufw en double
🟣 Pour l'option A (auditd) : commence par lire man audit.rules et la page auditd(8) avant d'écrire une seule ligne. Les règles auditd ont une syntaxe spécifique qui diffère de Bash.
